# カスタムマッチのチーム分け（Teams タブ）企画・設計書

カスタムマッチのロビーにいるメンバー（チームの枠と観戦枠）を League Client から読み取り、**今回の参加者**を選んで、**ランク**（未ランクの人は**過去の試合の味方・敵の平均ランクからの推定**）と**得意レーン**、**手動の設定（レーン固定など）**をもとに、バランスのよいチーム分けとレーン割り当てを提案する。結果は **Discord にそのまま貼れるコードブロック**でコピーできる。

- 状態: **企画（未実装）**。持ち主の回答（2026-11-27、§10）を反映済み。残りは §10.2 の未決事項。
- 決定番号は M-038 を予定（§11 は原案。decisions.md には未記入）。
- 前提として読むもの: [new-app-design.md](./new-app-design.md)（画面構成、MatchState と Workspace）、`next/CLAUDE.md`（ゾーン。`packages/lcu` は 🔴）。
- 作成: 2026-11-27。改訂: 2026-11-27（持ち主の回答を反映。事前取得とキャッシュ、Riot ID の入力、保存済みの一覧を追加。OP.GG は使わない。実機の LCU check の結果を §3.12 に反映）。

## 1. 結論（先に要点）

| 論点 | 案 |
|---|---|
| 置き場所 | Top bar に新しいタブ **Teams** を足す（`Viewers / Live Game / Teams / Settings`）。最初は Feature Flag `teamBalancer`（既定オフ） |
| メンバー | LCU の `/lol-lobby/v2/lobby` を GET＋購読する。カスタムロビーの **チームの枠・観戦枠の両方**を候補として読み、各人を「参加」「控え」に分ける（既定: チームの枠 = 参加、観戦枠 = 控え）。ユーザーが自由に入れ替えられる。ボットは除く |
| ランク | LCU の `/lol-ranked/v1/ranked-stats/{puuid}`。ソロ/デュオ → フレックス → **推定ランク**（§3.3）→ 前シーズン → 手動入力の順に使う |
| 推定ランク | 未ランクの人は、**直近のノーマルの試合に一緒にいた人（味方と敵）の今のランクの平均**を推定ランクとして使う。ランクがある人にも参考値として出す |
| 得意レーン | LCU の戦績から推定（第 1 段階から入れる）。**直近 20 試合**のうち、ランク戦・ノーマル（ドラフト / ブラインド / Swiftplay）だけを数える（§3.4） |
| 手動の設定 | プレイヤーごとに **レーン固定**・**得意レーン（上書き）**・**NG レーン**・**ランクの上書き**。PUUID に紐づけて保存し、次回のカスタムでも効く |
| 分け方 | 全通りを総当たりする（10 人で数ミリ秒）。**ランク重視の案とレーン重視の案を並べて出す**（各上位 3 案）。6・8 人もチーム分けする |
| Discord | 「Copy for Discord」でコードブロック形式の文字列をクリップボードへ |
| 事前取得 | カスタムの前（当日・前日）に、**フレンドのグループ**（または個別に選んだフレンド、今のロビーの人、**Riot ID の入力**で足したフレンドでない人）を指定して、推定ランク・ランク・得意レーンを**先に取ってキャッシュ**しておける（§3.7） |
| キャッシュ | キャッシュにある人は**一覧で見られ、人ごとにランク・推定の根拠の試合・レーンの回数まで開いて見られる**（§3.10）。端末内の 1 つの JSON ファイル（アプリのユーザーデータの場所）。**3 日以内なら新しい、14 日以内なら「古い」印つきで使う、30 日を過ぎたら捨てる**。推定に使う試合も直近 60 日以内に限る |
| OP.GG | **使わない**（開くボタンも、データの取得も。§3.3.3） |
| チームの自動移動 | **やらない**（§3.6）。提案を Discord に貼り、各自がクライアントで移動する |
| 安全面 | LCU は **GET だけ**。データは外部に送らない。`packages/lcu` の許可パスの追加は 🔴（人間のレビュー） |
| 確かめられないこと | 実際のカスタムロビーの JSON の形、他人の戦績が LCU で取れる範囲と件数、取得の速さ、Riot のポリシーの原文。**Windows 実機で確認が必要**（§9） |

## 2. やること / やらないこと

### 2.1 やること（第 1 段階）
- Teams タブ。カスタムロビーにいる間、候補者の一覧（Riot ID、ランク / 推定ランク、得意レーン、手動の設定）を「参加」「控え」に分けて出す。
- **参加 ⇄ 控えの入れ替え**: 観戦枠の人を参加に入れる、チームにいる人を外す。入れ替えたらすぐ提案を作り直す。ロビーの実際の枠は動かさない（アプリの中だけの選択）。
- プレイヤーごとの手動の設定（レーン固定 / 得意レーン / NG レーン / ランクの上書き）。保存して次回も使う。
- 戦績からの得意レーンと推定ランク。
- チーム分けの提案（ランク重視・レーン重視の 2 つの見方 × 上位 3 案。「別の案」。提案の中で 2 人を手で入れ替え）。
- 参加者が 6・8・10 人のとき（偶数）にチーム分けする。
- Discord 用のコピー（コードブロック形式）。
- 事前取得: フレンドのグループ / フレンドの個別指定 / 今のロビーの人 / Riot ID の入力を選んで、先に取得してキャッシュする（§3.7〜§3.9）。保存済みの人の一覧と中身の表示（§3.10）。
- ロビーにいないとき・カスタム以外のロビーのときは「カスタムロビーに入ると表示されます」と出す。手動でプレイヤーを足す欄も置く。

### 2.2 第 2 段階（使ってみてから決める）
- 「この 2 人は同じチーム / 別のチーム」の指定。
- 参加者が 10 人を超えたとき、誰が控えに回るかも含めて提案する。
- 奇数（7・9 人）への対応。

### 2.3 やらないこと（範囲外）
- LCU への書き込み（チームの移動、招待、キック、チャットへの自動投稿）。§3.6。
- OP.GG（開くボタン、MCP サーバー、ページの読み取りのどれも。持ち主の判断、2026-11-27。§3.3.3）。外部サイトの HTML の読み取りは、外部ビューに preload を渡さない規則にも反する。
- 隠れ MMR の表示。推定ランクは「一緒に試合をした人の公開ランクの平均」であって、MMR そのものではないと画面に書く。
- Discord への自動投稿（Bot / Webhook）。コピーして貼るのは人がやる。

## 3. 調査結果と方式

### 3.1 ロビーのメンバー
- `GET /lol-lobby/v2/lobby`（購読は `OnJsonApiEvent_lol-lobby_v2_lobby`）。**実機で確認済み**（§3.12）: カスタムロビーでは `gameConfig.isCustom` が `true`（`queueId` は `3100`）、`gameConfig.customTeam100` / `customTeam200` / `customSpectators` が各枠のメンバーの配列。要素は `puuid`、`isBot`、`isSpectator`、`summonerId`、`isLeader`、`botChampionId` など。
- ボットは `isBot: true` で `puuid` が空文字。トップの `members` は人間だけ（ボットは入らない）。
- 観戦枠の要素の形は未確認（観戦に人を入れられなかった）。チームの枠と同じ形と仮定し、`puuid` が無い要素は捨てる。
- 候補者 = `customTeam100` ＋ `customTeam200` ＋ `customSpectators` のうち、`isBot` でなく `puuid` がある人。
- 既定の振り分け: チームの枠の人 = 参加、観戦枠の人 = 控え。ユーザーが変えた振り分けは、同じロビーにいる間は保つ（ロビーの枠が動いても上書きしない。新しく入った人だけ既定で振り分ける）。ロビーを出たら忘れる。
- ロビーの要素には Riot ID（`gameName` / `tagLine`）が**無い**（`summonerName` も空）。名前は `GET /lol-summoner/v2/summoners/puuid/{puuid}` で取る（1ms。§3.12）。

### 3.2 ランク
- `GET /lol-ranked/v1/ranked-stats/{puuid}` で他人のランクも取れる（クライアントのプロフィール画面と同じ情報）。`queueMap.RANKED_SOLO_5x5` の `tier` / `division` / `leaguePoints` を使う。
- 使う順: ソロ/デュオ → フレックス → 推定ランク（§3.3）→ 前シーズンの最終ランク → 手動入力。手動の上書きがあれば最優先。
- 画面では、どれを使ったかを印で区別する（例: `G2`、`G2 (Flex)`、`~G3 (推定)`、`G1 (前季)`）。
- 点数化（案）: Iron IV = 0、1 ディビジョン = 100 点、LP を足す。Master 以上は Diamond I の上に LP をそのまま足す。

| ランク | 点（IV の 0LP） |
|---|---|
| Iron | 0 |
| Bronze | 400 |
| Silver | 800 |
| Gold | 1200 |
| Platinum | 1600 |
| Emerald | 2000 |
| Diamond | 2400 |
| Master+ | 2800 ＋ LP |

### 3.3 推定ランク（未ランクの人の、ノーマルでの「試合の平均ランク」）

#### 3.3.1 考え方
ノーマルのマッチングも内部のレートで近い人同士を集めるので、**一緒に試合をした人（味方 4 人 + 敵 5 人）のランクの平均**は、その人の実力の目安になる。OP.GG の試合詳細に出る「平均ティア」と同じ考え方。

#### 3.3.2 取り方（LCU だけで行う案）
1. その人の戦績の一覧（§3.4 と同じ取得）から、**直近 60 日以内**のノーマルを新しい順に**最大 10 試合**選ぶ（古い試合は今の実力とずれるので数えない）。
2. 各試合の詳細 `GET /lol-match-history/v1/games/{gameId}` で、その試合の 10 人の PUUID を得る。
3. 本人以外の 9 人のランクを取り、ソロ/デュオ（無ければフレックス）のランクを点にする。未ランクの人は数えない。ランクは **まとめて取れる** `GET /lol-ranked/v1/ranked-stats?puuids=...`（§3.11）を使い、全試合ぶんの PUUID から、キャッシュに無い人だけをまとめて取る。
4. 全試合ぶんの点の**中央値**を推定ランクにする（極端な人に引っ張られないように）。数えられた人が 15 人未満なら「データ少」と出し、推定ランクを使わずに前シーズン → 手動の順に回す。
5. 画面には「~G3（推定: 10 試合・72 人）」のように根拠の数も出す。

#### 3.3.2.1 取得する人数（推定は 1 段だけ。再帰しない）
推定ランクは「対象の人の過去の試合にいた人たちの**今のランク**」を使う。取得する人数は増えるが、次のように上限がある。
- **1 段だけ**: 一緒にいた人について取るのは、ランク（`ranked-stats`）1 回だけ。その人の戦績や、その人の推定ランクは取らない。一緒にいた人が未ランクなら、その人は数えずに飛ばす（推定の推定はしない）。
- **1 人の対象あたりの上限**: 戦績の一覧 1 回 + 試合の詳細 最大 10 回 + ランク 最大 90 回（10 試合 × 9 人）。
- **早めに止める**: ランクのある人を **40 人**数えた時点で、残りの試合は取らない（多くの場合 5〜6 試合で足りる）。
- **重なりはキャッシュで 1 回に**: 試合の詳細は gameId ごと、ランクは PUUID ごとに保存して使い回す。カスタム仲間は同じ試合・同じ相手が重なりやすい（自分の直近 21 試合で「最近一緒に遊んだ人」は 165 人）。
- **ランクがある対象には行わない**（参考値はボタンを押したときだけ）。

| 場面 | 取得の回数（最大） | 実測からの時間の目安 |
|---|---|---|
| 未ランク 1 人を推定 | 約 60〜100 回（早めに止めると 50 回前後） | 10〜25 秒 |
| 当日のロビー 10 人のうち未ランク 3 人 | 約 300 回（重なりで減る） | 1 分前後 |
| 事前取得 30 人（全員未ランクの最悪の場合） | 約 3,000 回（重なりで減る） | 10 分前後 |

- 他人のランクは 1 回 44〜168ms（Riot のサーバーへの中継あり）、試合の詳細は数 ms、戦績の一覧は 0.2〜1.8 秒（§3.12）。
- 「味方 4 人 + 敵 5 人」の 9 人を数える（マッチングは両チームを近いレートでそろえるため、味方も目安になる）。持ち主が「敵だけ」を望むなら、敵 5 人だけにする（数えられる人が半分になり、必要な試合が倍になる）。→ §10.2。

注意点:
- 取れるのは**今のランク**で、その試合をしたときのランクではない。シーズンの初めは未ランクの人が多く、数えられる人が減る。
- 取得の量: 1 人あたり 戦績の一覧 1〜2 回 + 試合の詳細 最大 10 回 + ランクのまとめ取り 数回（§3.11）。時間がかかるので、**カスタムの前に取っておける**ようにする（§3.7）。ロビーに入ったときは、キャッシュが新しければそれを使い、無いか古ければ、ランクと得意レーン（軽い）を先に取り、推定ランク（重い）は後から裏で取る。取れた人から表示と提案を更新する。
- LCU は Riot のサーバーへの中継なので、短い時間に投げすぎると遅くなる・断られる可能性がある。実機で速さと上限を確かめる（§9）。

#### 3.3.3 OP.GG は使わない（持ち主の判断、2026-11-27）
検討した案と、使わない理由の記録:
| 方式 | 良い点 | 悪い点 |
|---|---|---|
| LCU だけ（**採用**） | キー不要。外部に送らない。規約の心配が小さい | 取得の回数が多い。今のランクしか分からない |
| OP.GG の公式 MCP サーバー（`mcp-api.op.gg`、`lol-summoner-search` など） | 試合ごとの平均ティアなど、集計済みのデータがあるかもしれない | AI エージェント向けで、アプリから呼んでよいかの規約が不明。仕様が変わりやすい。Riot ID を外部に送ることになる |
| OP.GG のページを読み取る | — | 規約と安定性の面で不可 |

### 3.4 得意レーン（直近 20 試合）
- `GET /lol-match-history/v1/products/lol/{puuid}/matches?begIndex=0&endIndex=20` で**直近 20 試合**を取る（コミュニティの資料では 1 回で 20 件程度が上限とされる。実機で確認 → §9）。
- 数えるのはランク戦（ソロ/デュオ・フレックス）とノーマル（ドラフト / ブラインド / Swiftplay）。ARAM・カスタム・イベントモードは数えない。
- 数えられる試合が 10 未満なら、もう 1 回（21〜40 試合目）取って足す。それでも 5 未満なら「データ少」と出し、レーンの点数を弱める。
- 各試合のレーン/ロール（`timeline.lane` と `role` の組み合わせ）を TOP / JG / MID / BOT / SUP に直し、割合の高い順に「メイン」「サブ」とする。旧形式のフィールドなので BOT と SUP の判定が粗い可能性がある。持っているアイテム（サポートアイテム）とスマイトも手がかりに使う。
- 手動の「得意レーン」があれば、自動の推定より優先する。

### 3.5 手動の設定（プレイヤーごと、PUUID に紐づけて保存）

| 設定 | 意味 | 分け方での扱い |
|---|---|---|
| レーン固定 | 「この人は必ず JG」 | **必ず守る**（守れない組み合わせは出さない）。同じレーンの固定が 2 人なら別のチームに分ける。3 人以上なら警告を出す |
| 得意レーン | メイン / サブを手で決める | 自動の推定より優先 |
| NG レーン | 「SUP はやらない」 | 強いペナルティ（全員を満たせないときだけ破る。破ったら案に ⚠ を付ける） |
| ランク上書き | サブ垢・久しぶりの人など | 取得したランク・推定ランクの代わりに使う |

「参加 / 控え」はロビーごとの選択なので保存しない（§3.1）。保存先は既存の settings と同じ仕組み（`packages/core/src/settings.ts` の zod スキーマに `teamBalancer.players: Record<puuid, {...}>` を足す）。名前は表示用に、最後に見た Riot ID も持つ。

### 3.6 チームの移動を自動化できるか
- **自分自身**のチームの移動は、LCU の書き込み系の API（POST）でできるとされる（クライアントの「チームを移動」ボタンと同じ操作）。
- **他人を動かす**操作は、クライアントの画面にも無い（ホストでもできない）ため、API があるかも確認できていない。あったとしても非公開の動きに頼ることになる。
- このプロジェクトは「`packages/lcu` に書き込み系の API を足さない」規則（`next/CLAUDE.md`、🔴）で、読むだけのアプリとして作っている。自動化するにはこの規則を変える判断が要る。Riot のポリシー上も、クライアントの自動操作は避けるのが無難。
- → **やらない**。提案を Discord に貼り、各自がクライアントで移動する。

### 3.7 事前取得とキャッシュ

#### 3.7.1 使い方
1. カスタムの前（当日・前日など）に、アプリと League Client を起動してログインしておく（取得は League Client を通すので、クライアントが動いていないと取れない）。
2. Teams タブの「事前取得」で対象を選ぶ: **フレンドのグループ**（§3.8）、フレンドから個別に選ぶ、今のロビーにいる人、**Riot ID の入力**（フレンドでない人。§3.9）。
3. 「取得する」を押す。進み具合（`12 / 30 人・残り約 5 分`）を出し、裏で順番に取る。取得中も他のタブは使える。途中でアプリを閉じても、取れた人の分はキャッシュに残り、次に「取得する」を押すと続きから取る。
4. 当日ロビーに入ると、キャッシュにある人はすぐに推定ランクつきで並ぶ。

- 最後に選んだグループを覚えておき、次は 1 クリックで取り直せる。
- 一覧には各人の状態を出す: `取得済み（2 日前）` / `古い（9 日前）` / `未取得` / `取得中` / `失敗（理由）`。「古いものと未取得だけ取る」ボタンを既定にする。

#### 3.7.2 キャッシュ（端末内の JSON ファイル）
- 置き場所: アプリのユーザーデータのフォルダ（`%APPDATA%\LoL Viewer Next\` の下）に `team-cache.json` を 1 つ。設定ファイルとは分ける（消しても困らないデータなので）。
- 中身: PUUID ごとに、最後に見た Riot ID、ランク、得意レーン、推定ランク（根拠の試合数・人数）と、それぞれの**取得した日時**。他人のデータなので、端末の外には出さない（送らない、ログに書かない）。
- **試合ごとの結果も残す**（`gameId` → 試合の日時、キュー、その試合の 9 人の PUUID）。取り直すときは、キャッシュに無い新しい試合だけ詳細を取る。9 人のランクも PUUID ごとに共有のキャッシュに入れるので、仲間内で同じ人と遊んでいるほど速くなる。
- 書き込みは取得 1 人ごと（途中で閉じても残るように）。一時ファイルに書いてから置き換える（壊れたファイルを残さない）。読めないファイルは捨てて空から始める。
- 「キャッシュを全部消す」ボタンと、人ごとの「この人のデータを消す」を置く（シーズンの切り替わり、間違えて足した人など用）。
- キャッシュにある人は、一覧と中身を見られる（§3.10）。

#### 3.7.3 古さの扱い
| 経過（取得した日時から） | 扱い |
|---|---|
| 3 日以内 | 新しい。そのまま使う |
| 3〜14 日 | 使うが、`古い（9 日前）` の印を付ける。ロビーに入ったら裏で取り直す |
| 14〜30 日 | 提案には使わない（未取得と同じ扱い）。表示だけ灰色で残す |
| 30 日超 | 起動時にファイルから消す |

- 推定に使う試合は、取得の日時にかかわらず**試合の日付が直近 60 日以内**のものだけ数える。
- 推定に使う 9 人のランクは、3 日より古ければ取り直す。
- 上の日数は core の定数にまとめ、使ってみて変える。

### 3.8 フレンドのグループからメンバーを選べるか
- **できる見込み**。LCU の API の定義（コミュニティが公開している LCU の OpenAPI の定義）に、次の読み取りがある:
  - `GET /lol-chat/v1/friend-groups` … グループの一覧（`id`、`name`、`priority` など）
  - `GET /lol-chat/v1/friend-groups/{id}/friends` … そのグループのフレンド
  - `GET /lol-chat/v1/friends` … フレンド全員（`puuid`、`gameName`、`gameTag`、`groupId`、`groupName`、`displayGroupId` など）
  - 項目の名前は定義の要約から読んだもので、実際の JSON は実機で確認する（§9）。
- 画面: グループのドロップダウン（クライアントのフレンドリストで作った「カスタム勢」などのグループがそのまま出る）→ そのグループのフレンドが一覧に並ぶ → 全員にチェックが入った状態で「取得する」。個別にチェックを外せる。
- 自分自身も対象に含められる（自分はフレンドの一覧に出ないので、別に「自分を含める」のチェックを置く）。
- グループをアプリ側で作る機能は付けない（クライアントのフレンドリストで作ってもらう。LCU に書き込まない）。
- フレンドでない人は、Riot ID の入力で足す（§3.9）。

### 3.9 Riot ID の入力でフレンドでない人を足す（持ち主の判断、2026-11-27）
- 事前取得の欄に入力欄を置く。`名前#タグ` を 1 行に 1 人（Discord などから貼り付けた複数行もそのまま受け付ける）。`#` が無い行は「タグがありません」と赤く示す。
- Riot ID から PUUID を引くのに、LCU の読み取りの API を使う。LCU の定義に Riot ID（名前とタグ）を受け取ると明記された読み取りは**見つからなかった**。候補は `GET /lol-summoner/v1/summoners?name=名前%23タグ`（`name` が Riot ID を受け付けるかは定義からは分からない）。実機で確かめる（§9）。見つからなければ「見つかりません」と出し、その行だけ残す。
- 引けた人は「足した人」としてキャッシュに Riot ID と PUUID を残す（30 日で消えるのは他のデータと同じ。取り直せば延びる）。次回からは入力しなくても、事前取得の対象の一覧（「足した人」）から選べる。
- Riot ID は変えられるので、表示は PUUID で人を区別し、名前は最後に見たものを出す。名前が変わっていたら `旧: Alice#JP1` を小さく添える。
- 公式の Riot API（account-v1、API キーが必要）は使わない（§3.4 の方式 B と同じ理由）。もし LCU で Riot ID を引けなかった場合の代わり（§10.2）: (1) `GET /lol-match-history/v1/recently-played-summoners`（最近一緒に遊んだ人の一覧）から名前で選ぶ、(2) キャッシュにある人（同じロビーにいたことがある人）の名前から選ぶ。

### 3.10 キャッシュにある人の一覧と中身
- 事前取得の欄に「保存済み（23 人）」のタブを置き、キャッシュにある人を一覧で出す。列: Riot ID、ランク（ソロ / フレックス）、推定ランク、メインのレーン、取得した日（新しい / 古い / 使わない の色分け）、手動の設定の有無。並べ替え（名前・ランク・取得日）と名前の検索ができる。
- 行を開くと中身を出す:
  - **ランク**: ソロ / フレックス / 前シーズン（それぞれ tier・division・LP）と取得日時。
  - **推定ランク**: 値、数えた試合数と人数、点の分布（最低・中央・最高）、試合ごとの一覧（日付、キュー、その試合の 9 人のランクの中央値、数えた人数）。
  - **得意レーン**: 数えた試合数と、レーンごとの回数・割合（横棒）。
  - **手動の設定**: レーン固定・得意・NG・ランク上書き（ここからも編集できる）。
  - 操作: 「この人を取り直す」「この人のデータを消す」。
- この一覧はロビーにいなくても見られる。

### 3.11 LCU の要求の量とレート制限（実装の参考）

#### 3.11.1 調べて分かったこと（2026-11-27）
- **LCU（手元のクライアントの API）のレート制限の数値は、公式にもコミュニティにも見つからなかった。** LCU の OpenAPI の定義にも、制限の記述は無い。
- ただし、戦績・ランク・サモナーの情報は、LCU が Riot のサーバーへ中継して取ってくるもので、手元だけで完結しない。利用者の報告として、LCU が `TOO_MANY_REQUESTS`（「取得が速すぎるので待て」）を返した例がある（出典が弱く、どの API・何回で出たかは不明）。
- 参考: Riot の公開 API（API キーで使う方）の開発用キーの上限は「1 秒 20 回・2 分 100 回」。LCU に同じ上限があるわけではないが、強めに絞る目安として使う。
- 公開 API の利用者の資料では、429（多すぎる）を受けたら 1 秒 → 2 秒 → 4 秒…と待つ間隔を延ばす、試合の詳細は終わった試合なら変わらないのでキャッシュする、が定番。
- 要求の量を減らせる API が見つかった:
  - `GET /lol-ranked/v1/ranked-stats?puuids=...` … **複数人のランクを 1 回で取れる**（PUUID の配列 → PUUID ごとのランク）。1 回に何人まで入れられるかは不明。
  - `GET /lol-chat/v1/friend-groups/{id}/friends` … グループのフレンドだけを取れる。
  - `GET /lol-summoner/v1/summoners-by-puuid-cached/{puuid}` … クライアントがキャッシュしているサモナーの情報（中継しない可能性がある）。
- 戦績の一覧 `.../matches` は `begIndex` / `endIndex` を取るが、上限は定義に書かれていない（コミュニティでは 20 件程度とされる）。

#### 3.11.2 実装の方針（数値は使ってみて変える。core の定数にまとめる）
| 項目 | 方針 |
|---|---|
| 同時に投げる数 | 2（ロビーに入ったときの軽い取得は 4） |
| 間隔 | 1 秒に 5 回から始め、**断られず応答も遅くならない間は少しずつ上げる**（上限 1 秒 20 回）。429 が出たり応答が 1 秒を超えたりしたら半分に下げる。Rate test は手元の値しか測れなかったため（§3.12） |
| ランク | 1 人ずつ取る（まとめ取りの API は実機で 404。§3.12） |
| 429 / 503 | `Retry-After` があればそれに従う。無ければ 2 秒から倍々、上限 60 秒（既存の LCU の再接続と同じ考え方）。同じ要求は 3 回まで |
| 連続で断られたら | 3 回続けて 429 なら事前取得を 60 秒止め、画面に「League Client から取得を制限されました。1 分後に再開します」と出す |
| キャッシュ | 試合の詳細は変わらないので、一度取ったら取り直さない。ランクは 3 日（§3.7.3） |
| 優先順位 | ロビーにいる人の軽い取得（ランク・レーン）> ロビーにいる人の推定 > 事前取得 |
| 計測 | 要求ごとに経過時間と結果（成功 / 429 / その他）を数え、Settings の Debug 欄に「直近の取得: 312 回・429 が 0 回・平均 180ms」を出す（実機での調整用。中身や PUUID は出さない） |

見積もり（実機で測る前の目安）: 推定ランクは 1 人あたり十数回の要求。1 秒 5 回なら 1 人 3 秒前後、30 人で 2 分前後（中継の遅さは含まない。仲間内で同じ人が多いほど速い）。→ §3.12 の実測で見直した。

#### 3.12.1 設計の変更
- **戦績は直近 20 試合ほどしか取れない**ので、得意レーンと推定ランクは「取れた試合をキャッシュに貯めて、直近 60 日の分を数える」にする（§3.7.2 の試合ごとの保存をそのまま使う）。事前取得やロビーでの取得をするたびに新しい試合が増えていく。初回は最大 20 試合ほど。
- 数えるキュー（決め打ち。それ以外は数えない）: `400`（ドラフト）、`420`（ソロ/デュオ）、`430`（ブラインド）、`440`（フレックス）、`480`（Swiftplay）、`490`（クイックプレイ）。推定ランクに使うのはノーマル（`400`・`430`・`480`・`490`）。
- レーンの変換: `TOP` → TOP、`JUNGLE` → JG、`MIDDLE` / `MID` → MID、`BOTTOM` + `CARRY` / `DUO_CARRY` → BOT、`role` が `SUPPORT` / `DUO_SUPPORT`（`lane` は `NONE` も `BOTTOM` もある）→ SUP。それ以外（`NONE` / `NONE` など）は数えない。サポートアイテムとスマイト（`spell` の `11`）で補う。
- ランクのまとめ取りは使わない。1 人ずつ（PUUID ごとに 3 日キャッシュ）。§3.11.2 の「ランク」の行を改める。
- フレンドのグループは `/lol-chat/v1/friends` の `groupId` / `groupName` で絞る（グループごとの API は使わない）。
- 事前取得の対象に「最近一緒に遊んだ人（165 人程度）」の一覧からの選択を足す（名前で検索）。
- 見積もり（実測から）: 戦績の一覧は 1 人の初回 1.5〜2 秒、試合の詳細とランクは数 ms〜数十 ms。推定ランク 1 人（一覧 1 回 + 詳細 最大 10 回 + ランク 最大 90 回、間隔 200ms）でおよそ 20〜25 秒。30 人なら 10 分前後。**事前取得が要る**という見込みは変わらない。間隔を詰められるかは Rate test の結果で決める。

## 4. 分け方（アルゴリズム）

参加者が N 人（6・8・10）のとき:
1. チームの組み: N 人から N/2 人を選ぶ通り数 ÷ 2（青赤の入れ替えは同じ）。10 人で 126、8 人で 35、6 人で 10 通り。
2. レーンの割り当て:
   - 10 人: 各チームで 5! = 120 通り。チームごとに独立に最良を選べるので、計算は 252 × 120 ≒ 3 万回。総当たりで数ミリ秒。
   - 6・8 人: レーンは割り当てない。代わりに、各チームで「メインのレーンが重ならないか」を点数に入れ、案の中に各人のメインのレーンを並べて出す（3v3・4v4 は遊び方がいろいろなので、使ってみて見直す）。
3. 点数（小さいほどよい）:
   - `ランク差` = |青の平均点 − 赤の平均点|
   - `レーン適性` = 各人に「固定 0 / メイン 0 / サブ 小 / その他 中 / NG 大」のペナルティを足す（6・8 人ではメインのレーンの重なりのペナルティ）
   - `対面差` = 各レーンの対面同士のランク点の差の合計（10 人のみ。1 レーンだけ大差になるのを防ぐ）
   - `合計 = w1 × ランク差 + w2 × レーン適性 + w3 × 対面差`
4. **2 つの見方で並べて出す**（持ち主の判断、2026-11-27）:
   - **ランク重視**: w1 を大きく。まずチームの平均ランクをそろえ、その中でレーンを合わせる。
   - **レーン重視**: w2 を大きく。まず全員をメインのレーンに入れ、その中でランクをそろえる。
   - それぞれ上位 3 案。2 つの見方で 1 位の案が同じなら「同じ案」と表示する。
5. 「別の案」を押すと、最良から一定の幅に入る案から順に出す（毎回同じ人と組まないように）。
6. 参加者が奇数・4 人以下・11 人以上のときは提案を出さず、「参加者を 6・8・10 人にしてください」と出す（第 2 段階で見直す）。

この計算は `packages/core` の純粋な関数（`balanceTeams(players, options) => { rankFirst: Proposal[]; laneFirst: Proposal[] }`）にして、テストで固める。

## 8. テスト
- core: ランクの点数化、推定ランク（中央値、データ少のとき）、レーン推定（キューの絞り込み、BOT/SUP の判定）、固定・NG の制約、10 / 8 / 6 人、固定の衝突、ランク重視とレーン重視で結果が変わる例、Discord 文字列（スナップショット、2000 文字の上限、全角の幅）。
- core: キャッシュの古さの判定（3 / 14 / 30 日の境目）、60 日より古い試合を数えないこと、壊れたキャッシュを読んだら空になること。
- hub: 合成のロビーイベントから、観戦枠が控え、ボットが除外になること。ロビーの枠が動いてもユーザーの振り分けが保たれること。事前取得: グループのフレンドだけが対象になる、取得済みの試合の詳細は取り直さない、中止して再開すると続きから取る。
- web: Teams ページの stories（ロビーなし / 取得中 / 10 人 / 観戦あり / 8 人 / 人数が合わない / 警告あり）と Storybook の E2E、スクショを目で確認。
- Electron の E2E: fake-lcu のカスタムロビーで Teams に候補者が出て、控えを参加に入れると提案が変わり、コピーできること。

## 11. 決定: M-038（原案）

## M-038 カスタムマッチのチーム分け（Teams タブ、Feature Flag、2026-11-27）
- Teams タブを足す。カスタムロビーのチームの枠と観戦枠の人を候補にし、ユーザーが参加 / 控えを選ぶ（既定: チームの枠 = 参加、観戦枠 = 控え。ボットは除く）。
- ランク（未ランクの人は直近のノーマル 10 試合の一緒にいた人のランクの中央値で推定）と得意レーン（直近 20 試合のランク戦・ノーマル）と手動の設定から、ランク重視・レーン重視の 2 つの見方でそれぞれ上位 3 案を出す。6・8・10 人に対応する。Discord 用のコードブロックをコピーできる。Feature Flag `teamBalancer`（既定オフ）。
- カスタムの前に、フレンドのグループなどを指定して推定ランクなどを事前に取り、端末内の JSON ファイルにキャッシュできる（3 日以内は新しい、14 日以内は「古い」印つき、30 日超は捨てる。推定に使う試合は直近 60 日以内）。
- データは LCU の GET だけ（ロビー、フレンドとグループ、ランク、戦績、試合の詳細）。LCU への書き込み（チームの移動を含む）、外部サイトの HTML の読み取り、外部への送信はしない。
- 手動のレーン固定は必ず守る。NG レーンは全員を満たせないときだけ破り、⚠ を付ける。
